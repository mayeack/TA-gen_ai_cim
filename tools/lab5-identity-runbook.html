Lab 5 runbook — Cisco Identity Intelligence on a room stack (TA-gen_ai_cim 1.8.0)

AI Trust Lab 5 ("Verify: Cisco Identity Intelligence") on one Splunk Show room stack: Cisco Identity Intelligence (CII) reports the room's victim persona as taken over, PseudoCo Assistant 4.22.0+ refuses the victim's signed-in turns, Splunk ES joins the CII failed checks with Cisco AI Defense blocks, and SOAR disables the victim in Duo. Everything Lab 5 adds to the TA ships off; this runbook turns it on for one stack and off again.

Run it from a checkout of the TA (tools/ is not in the package). One run per room stack. Never on a customer stack.

Before the takeover (T-4 at the latest)

  1. Cisco Security Cloud app 3.7.3+ (3.x) or 4.1.3+ (4.x) on the stack.
  2. CII input in that app: Cisco Identity Intelligence → Configure Application, connection method Webhook, index cisco_identity_intelligence (step L1 below creates it; run --lab5 first if it does not exist yet). In Identity Intelligence, assign the webhook to MFA Flood, Impossible Travel and Duo Sign In Threat Detected, and run its connectivity test: a WebhookTest event must arrive (the TA drops it from the detection on purpose).
  3. This must exist before the T-2 takeover: CII webhooks announce only newly failing users.

--lab5 (per room stack)

export SPLUNK_ADMIN_PASSWORD='...' SPLUNK_ACS_TOKEN='...' SOAR_PASSWORD='...'
export DUO_IDENTITY_OPS_API_HOST='api-XXXXXXXX.duosecurity.com'
export DUO_IDENTITY_OPS_IKEY='...' DUO_IDENTITY_OPS_SKEY='...'
python3 tools/show_postdeploy.py --stack https://<stack>.splunkcloud.com \
    --soar-url https://<tenant>.soar.splunkcloud.com \
    --lab5 --lab5-victim <victim persona> --lab5-room <workshop>-<room> \
    --out <room>-stack.json --dry-run

Drop --dry-run once the report reads right. The Duo keys are the PseudoCo Identity Ops Admin API application (Grant resource read + write). They are read from the environment only, never from argv, and only their last four characters are printed.

T-1: is the victim's evidence in the stack?

`genai_cii_failed_checks` | search identity_user="<victim>"
| table _time, cii_check, cii_trust_level, cii_provenance

At least one row for MFA Flood or Impossible Travel. If CII never sent it:

  1. In CII Check Results, use the victim's Send notification for each failing check (CII re-sends the real event).
  2. Otherwise the Lab 5 setup tool writes a labelled backfill from the CII API into the same index, with source=lab5-setup and "backfill": true in the event body. The rule accepts it and the finding says cii_provenance = backfill (lab5-setup).
  3. Never synthetic events in a room stack. "synthetic": true is for test stacks only, and the finding labels it synthetic test event.

Lab day

  • The spray aimed at the victim raises three findings: the Lab 4 prompt-injection correlation, the ES 24-hour risk threshold and the Lab 5 rule GenAI Compromised Identity: . Work the Lab 5 one.
  • Containment prompt for the ES agent (Guided Response 8.6, AI SOC analyst 8.7, Triage and Response 8.8): "Using PseudoCo Identity, disable user . Reason: compromised identity". If it picks the MedAdvice simulator, that app now fails with "managed by PseudoCo Identity".
  • Verify: PseudoCo Identity → get user reads disabled, and the victim's PseudoCo Assistant sessions show the revocation banner (identity_session_revoked). Unblock me restores an attendee's app session but leaves Duo disabled; the finding's evidence is unchanged.
  • Dashboard: AI Governance → Dashboards → Compromised Identity.

Teardown

python3 tools/show_postdeploy.py --stack https://<stack>.splunkcloud.com \
    --soar-url https://<tenant>.soar.splunkcloud.com --lab5-teardown

It disables the rule, the persona input and the seed switch, and deletes the pseudoco_identity asset with its Duo secret. Then, by hand: delete the Security Cloud CII input (that unregisters the webhook) and confirm the target is gone in Identity Intelligence before the stack is destroyed; revoke the stack's CII API client; rotate the Identity Ops keys after the workshop.
